## Project Overview
Kindura AI: Flutter health/wellness app with LiveKit voice AI integration. MVVM + Repository pattern with GetX state management. Professional Ornament-inspired theme with comprehensive medication tracking, lab reports, and voice-controlled health monitoring.

## Local Development Setup
The project is configured for local development with PostgreSQL database for production-ready testing:

### Quick Start:
```bash
./setup_local.sh      # Run once to set up environment (installs PostgreSQL, creates DB)
./startkindura.sh      # Start all services (PostgreSQL, Django API, LiveKit, Flutter)
```

### Configuration:
- **Database**: PostgreSQL (`localhost:5432/kindura_db`)
  - User: `kindura_user`
  - Password: `kindura_pass`
  - Configured via environment variables in Django settings
- **API URL**: Configurable via `lib/res/app_url/app_url.dart`
  ```dart

  ```
- **Authentication**: Token stored in `.env.local` (auto-generated by setup script)
- **File Uploads**: Stored locally in `media/` folder
- **Environment**: All data stays on local machine for testing

3. Token is never hardcoded in source code
4. Each developer has their own local token (not shared)

## Medication Adherence Tracking System

### Daily Tracking Logic
At the start of each day:
- **Pending** = Total number of active medications in DB for the user
- **Taken** = 0
- **Missed** = 0

As the day progresses:
- When user marks a medication as taken (via app or voice):
  - **Taken** increases by 1
  - **Pending** decreases by 1
  - Timestamp of actual taken time is recorded
  - If taken_time ≠ scheduled_time → mark as "late" for reporting
- By end of day:
  - **Pending** should equal 0
  - **Taken** should equal total medications
  - Any remaining pending at end of day → converted to **Missed**

### Recording Medication Status
Medications can be marked as taken via:
1. **Manual Entry**: User taps "taken" button in medication tab
2. **Voice Command**: User tells LiveKit agent "I took my [medication name]"
   - Agent calls `/api/dose-events/` endpoint
   - Creates `MedicationEvent` with status='taken' and actual timestamp

### Data Captured for Each Dose Event
- `medication_id`: Which medication was taken
- `scheduled_at`: When it was supposed to be taken
- `taken_at`: When it was actually taken (null if missed)
- `status`: 'taken', 'missed', 'late', 'skipped'
- `notes`: Any user notes or side effects reported

### Reporting & Analytics
This tracking data feeds into:
- **Daily Reports**: Adherence rate, on-time vs late doses
- **Weekly Reports**: Patterns, missed medications, concerning trends
- **Monthly Reports**: Long-term adherence, medication effectiveness
- **Side Effect Correlation**: Link missed doses to reported side effects
- **Doctor Insights**: Help physicians identify problematic medications or schedules

### Important Considerations
- A missed dose can still be taken late (status changes from 'scheduled' to 'late')
- Side effects should be correlated with both taken and missed medications
- Time zone handling is critical for accurate scheduling
- Only events from **active** medications are counted in adherence summary

## Common Build Errors & Fixes
- **Missing Colors import**: Add `import 'package:flutter/material.dart';` to controllers
- **TranscriptionSegment properties**: Use boolean value instead of `segment.final_` or `segment.final`
- **Const expression errors**: Remove `const` from widgets with dynamic properties like `Colors.green.shade50`
- **ConnectionState import conflict**: Use `import 'package:livekit_client/livekit_client.dart' as livekit;` and prefix LiveKit types
- **iOS Simulator audio**: Test LiveKit audio on physical device, not simulator
- **File picker warnings**: Platform-specific warnings are safe to ignore for iOS-only builds

## Voice Trigger Issues & Solutions
- **"Kindura" not recognized**: Added fuzzy matching for pronunciations like "i can do it", "i can dura"
- **Agent greeting delay**: Added 1-second delay before greeting to ensure client audio is ready
- **Turn-taking problems**: Adjusted VAD and turn detection settings for better conversation flow
- **No audio output**: Must call `audioTrack.start()` on subscribed audio tracks and enable `speakerOn: true` in RoomOptions

## Agent Error Patterns & Fixes
- **VAD.load() invalid parameters**: `threshold` parameter not supported - use only `min_silence_duration` and `min_speech_duration`
- **Agent crashes silently**: Added comprehensive error logging with emojis for better debugging
- **Performance monitoring**: Built-in monitoring tracks connection times, audio setup, and conversation flow

 ## Toon Format (Token-Optimized JSON)

When generating or reading structured data, always use the **Toon** format unless stated otherwise. Toon is a token‑optimized JSON schema that replaces long field names with short, stable keys to reduce token usage, increase speed, and improve consistency.

---

## 1. General Rules for TOON and JSON
- App customer experience rule:  Do not let the user get stuck on any app screen while you are analysing in the baground, he should always be free to navigate while you are processing in the background ( Ex : when he upload files to the app the app should first upload quickly and then analyse the files in the background, when done the app should notify user.)
- always put a time stamp in front of the changes when you are updating changes.md even if you group the changes daily or weekly etc when you optimize.
- Use short keys (1–3 characters)
- Avoid long JSON field names
- Prefer arrays over objects when possible
- Use compressed timestamps (YYYYMMDD or UNIX epoch)
- Represent categories with short codes  
  - "u" = user  
  - "a" = assistant  
  - "s" = system  
- Avoid unnecessary whitespace, comments, or natural text around Toon objects
- The model must always output Toon when structured data is needed
- Always keep track of all the changes you make in a changes.md file and refer to it if you got disconnected or if you lost track. Make sure to timestamp the content of changes.md
- Always read changes.md to check what was the latest changes

---

## 2. Standard Toon Schema

```
{
  "id": <int>,       // identifier
  "r": <str>,        // role: u/a/s
  "c": <str>,        // content/message
  "t": <int>,        // timestamp (epoch)
  "m": <object>,     // metadata with short keys
  "y": <str>         // item type: msg, lab, med, note, ev
}
```

## 4. Extended Key Reference

- `id` = unique identifier  
- `r` = role  
- `c` = content  
- `t` = timestamp  
- `m` = metadata  nchec
- `y` = data type  
- `v` = value  
- `u` = unit  
- `ref` = reference id  
- `e` = embedding vector

## 5. Developer Instructions (Internal)

When interacting with the DB or RAG:
- Convert full JSON → Toon before sending to the model
- Convert Toon → JSON after receiving model output
- Validate that output conforms to Toon schema
- Reject or correct non‑Toon verbose JSON
- Use Toon for all structured data:  
  - Conversation logs  
  - Medical timeline events  
  - Lab and imaging data  
  - Medication response notes  
  - Patient summaries  
  - Monthly reports  
  - Memory objects  
  - Agent tool outputs
